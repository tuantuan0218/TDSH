## P1 换牌分档（快攻系对手收紧）—— ~20 行

**现状**（L142）：`val keepMaxCost = 3` 一刀切，对手职业读了但不用（L147 只打日志）。
**证据**：猎 4/6 败=3-5min 速败；对快攻起手 3 费牌太慢。

```kotlin
// L142 处替换：
val rivalHero = try { WAR.rival?.playArea?.hero?.cardId } catch (e: Throwable) { null }
// 快攻系（猎人内战/术士自残快攻/盗贼连击/恶魔猎手）=实践模式 AI 里前 4 回合压脸最快的 4 个职业
val isAggroMatchup = rivalHero in AGGRO_HERO_IDS
val keepMaxCost = if (isAggroMatchup) 2 else 3
// 类常量（放伴生对象）：
// val AGGRO_HERO_IDS = setOf("HERO_05", "HERO_07", "HERO_03", "HERO_10")
```

**加分项（保场面）**：换牌后若手里一张随从都没有（全法术/技能牌），强制换掉最贵的一张找随从（T1-T2 空过=速败根源）：
```kotlin
val hasMinion = hand.any { isMinionCard(it.cardId) }  // 需 CARD_DATA_TRIE 查 cardType；拿不到则跳过此增强
if (!hasMinion && swap.isEmpty() && hand.size >= 3) {
    val drop = hand.last()  // sortedBy cost 后最贵的
    cards.remove(drop); log.info { "[DrawFix] 换牌补随从: 无随从起手 → 换最贵 ${drop.cardId}(${drop.cost}费) 找场面" }
}
```
**验收锚（日志）**：`换牌分档: 对手=$rivalHero 快攻=$isAggroMatchup keepMaxCost=$keepMaxCost`；对 HERO_05/07/03/10 时 keepMaxCost=2 的决策行 ≥1。
**风险**：低——rivalId 换牌期可能为 null（L148 已有 try 兜底），null 时回落 3。

## P2 英雄技能优先级 —— ~30 行

**现状**：技能无优先级，只跟官方 options 放行走（`heroPowerUsed` 标记存在但未见主动排序）。
**证据**：术士 40min 败局技能仅 5 次（分流=牌源自断）；猎速败局稳固射击 2-3 次（空场时它是唯一输出）；盗贼 0.8/回合接近该有的密度。

**设计**：在主环候选排序后、cardLoop 前插一个「技能窗口」判断（不插入 candidates 内——技能不是手牌卡，须独立通道）：

```kotlin
// 放在 L276（出牌排序日志）之后、cardLoop 之前：
// P2 技能窗口（m2v200 草案）：满足全部条件才点技能，一次一迭代只点一次（heroPowerUsed 已有防重）
if (!heroPowerUsed && totalPlays == 0 && iterations >= 2) {   // 先让卡牌路径跑两轮，确认无卡可出才动技能
    val myHero = WAR.me.playArea.hero?.cardId
    val enemyMinions = try { WAR.rival?.playArea?.cards?.size ?: 0 } catch (e: Throwable) { 0 }
    val shouldPower = when (myHero) {
        "HERO_07" -> true                                    // 术士：生命分流=过牌，有富余费就点（每回合）
        "HERO_05" -> enemyMinions == 0                       // 猎人：稳固射击只在敌空场（无场面交互收益时才走脸）
        "HERO_03" -> true                                    // 盗贼：匕首每回合都值（0 费装备）
        else -> false                                        // 其余职业维持现状（样本不足不瞎改）
    }
    if (shouldPower && me.usableResource >= 2 - (if (myHero == "HERO_03") 1 else 0)) {
        // 官方 options 必须列 HERO_POWER 可执行（沿用 officiallyExecutable 门，不绕）
        if (officiallyExecutable(-1, optGate) /* 或技能实体判据 */) {
            CardAction.useHeroPower()   // 或 actuator 现有技能调用入口
            heroPowerUsed = true; roundBusy = true
            log.info { "[DrawFix] P2技能窗口: $myHero 点技能（职业策略 $myHero / 敌随从=$enemyMinions）" }
        }
    }
}
```

**注意**：技能的实际调用入口需 Ryan 对 SDK 确认（`CardAction.useHeroPower` 是示意名）——DSH 只读过 CardAction.kt:86 攻击行，技能调用未在日志中见到独立入口。**这段伪码必须由 Ryan 用真实 API 名重写**，条件逻辑可保留。
**验收锚**：`P2技能窗口` 日志出现 + 术士局技能/回合 ≥1.5（40min 败局基线 5/9=0.56）。

## P3 回合末预算清零（穷尽自门复核）—— ~15 行

**现状**：穷尽自门（L645 附近）把「预算不足」的卡计入剔除集判穷尽收工；但预算是自记账（spentManaThisTurn 含半落地虚占），半落地未销账时预算是**虚低**——实际游戏里还有水晶可花。
**证据**：败局挂账回合占比 88-100%（几乎每回合末都有虚占）；速败局等不到下回合补偿。

**设计**：穷尽自门触发前加一道复核——若剩余预算 + 半落地虚占之和 ≥ 手中最低费可执行卡，且官方 options 对该卡无 REQ_ENOUGH_MANA（新块亲口可付），则**先点它再收**：

```kotlin
// 穷尽自门分支（L645 附近）在 ledger["穷尽自门"]++ 之前插：
val virtualHeld = halfLandedCost.values.sum()   // 半落地虚占的费用
val realBudget = budgetRemaining() + virtualHeld
val cheapest = candidates.minByOrNull { it.cost }   // 注意：穷尽自门处 candidates 需在作用域内（如不在则重取 me.handArea）
if (cheapest != null && cheapest.cost <= realBudget && cheapest.entityId !in costRejected) {
    log.info { "[DrawFix] P3预算复核: 虚占=${virtualHeld}费 实余=$realBudget ≥ ${cheapest.cardId}(${cheapest.cost}费)官方未拒 → 先出再收（m2v200 草案）" }
    return@executeOutCard /* 不收工，走正常兜底点击路径出这张卡 */
}
```

**风险**：中——「先出再收」会延长回合 ~2s，但相比半落地跨回合慢一拍的代价是赚的；且仅当官方新块亲口未拒才放行（有 m2v197 复核门兜底，不会点废牌）。
**验收锚**：`P3预算复核` 出现且下回合首动作不再是「旧账优先销账」堆积（`_loss_review_quant.py` 挂账回合占比从 88-100% 显著下降）。
