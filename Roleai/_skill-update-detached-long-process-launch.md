## When to Use
- 会话内要启动任何超出单次工具调用生命周期的长驻进程：监控 watcher、本地服务/服务器、游戏或交易自动化宿主脚本等。
- 长驻进程出现「静默退出」：无 ERROR 日志、无崩溃栈、exit code 1 或干脆消失时，先按本 skill 诊断，再怀疑程序自身 bug。

## Prerequisites
- 理解本环境机制：从工具调用里 spawn 的进程属于该调用的进程树；调用中止/超时/被回收时，整棵树被连坐终止（实测两次复现：脚本静默退出，根因均为父级调用中止，而非程序缺陷）。
- 启动前准备：把 stdout/stderr 重定向到盘上日志文件，别只依赖会话内回显——会话一断，取证材料就没了。

## Procedure
1. 静默退出诊断顺序：先查「谁拉起了它」——若由某次工具调用启动，优先判定连坐回收；再查崩溃转储/错误栈（真实崩溃会有痕迹）。连坐回收的特征：无错误栈、退出时机与某次调用中止吻合、可稳定复现。
2. 防连坐启动方式，按序选：
   a. managed background job / 环境原生独立后台任务机制；
   b. 最稳兜底：用户手动双击 .bat/.cmd 启动，agent 只做值守（盯日志、核台账/结果）；
   c. 实在要 agent 当场启动：重定向输出到日志文件，并把关键进度落盘，接受随调用结束而死的风险、可重启恢复。
3. 启动后验证存活：观察窗必须超过历史死亡时长，日志持续追加、任务有实际推进，才算启动成功。
4. 交接文档把启动步骤写成用户可独立复现的形式（双击路径、参数、验证点），不要只存在于会话记忆里。

## Pitfalls
- 最大坑：把连坐死误判为程序自身 bug（如误疑字节码补丁引发 JVM 校验崩溃），白白回滚已验证生效的正确改动。
- 长驻进程关键状态只存内存：被杀后无法恢复——状态必须定期落盘，重启可从快照恢复。
- 用阻塞式长命令在工具调用里「顺便」跑起服务，等于给它签死刑。
- 「静默退出无日志」≠ 程序 bug：先排除父级生命周期，再查程序本身。
- **`.cmd`/`.bat` 启动脚本禁止写中文注释（实测踩坑）**：cmd.exe 按系统代码页（GBK）解析
  批处理，UTF-8 中文注释会被乱码拆成非法命令（实测报 `'y.log（同目录，stdout' is not
  recognized...`，启动被打断）。交付给用户双击的 `.cmd` 一律用纯 ASCII 注释/echo；
  需要中文说明就放同目录 README.md，不放批处理里。写完必须实际跑一遍（含中文环境），
  看是否出现 `is not recognized` 报错，再交接。
- **含中文的 `.ps1` 必须存为 UTF-8 with BOM（同类坑的 PowerShell 版本，实测踩坑）**：
  无 BOM 时 PowerShell 5.1 按 GBK 解码 UTF-8，中文字符被拆错导致**解析器内部行号/列偏移**，
  表现极具迷惑性——脚本花括号明明配平，却报 `Missing closing '}' in statement block`，
  且**报错行号比实际少若干行**（实测报 144 行、真语句在 146 行）。
  这会把排查引向根本不存在的语法错误，实测耗费大量时间。
  诊断捷径：**用 `ParseInput` 与 `ParseFile` 分别解析同一文本；两者结论不一致即可判定是编码问题而非语法问题**
  （实测 `ParseInput` 通过、`ParseFile` 报错，而直接执行同样失败）。
  修复：`[System.IO.File]::WriteAllText($p, $raw, (New-Object System.Text.UTF8Encoding($true)))`。
  **注意 `edit`/`write` 工具改过含中文的 `.ps1` 后可能丢失 BOM，改完必须复检并补回。**
  另注：Node 侧脚本（如本地服务器的 `serve.js`）按 UTF-8 原生读取，**不需要** BOM。
  相关：交付脚本若被别的脚本引用，路径一律用 `$PSScriptRoot`/`__dirname` 相对解析，
  别硬编码绝对路径，否则整目录搬迁后会写回旧位置。

## Verification
- 进程存活时长超过历史死亡间隔，日志文件仍在追加。
- 人为中止一次承载它的调用，确认进程不受影响（防连坐成立）。
- 任务级验证：台账/对局/产出有实际推进，而非仅进程存活。
