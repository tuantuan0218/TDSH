# xzt 限流实测修正：不止"10 次/分钟" — 2026-09-13

> 承接本轮：验证池内 5 个映射时，第 4、5 项开始遇到持续 429。
> 深挖后发现**我此前对限流的理解不完整**，特此修正。

## 一、观察到的现象

用已验证可用的模型（`Qwen/Qwen2.5-7B-Instruct`）**每 10 秒探一次**（=6 次/分钟，低于我以为的 10/min 上限）：

```
23:16:37 第1次: HTTP 429 code=ip_throttled
23:16:47 第2次: HTTP 429
23:16:57 第3次: HTTP 429
...
23:18:32 第12次: HTTP 429
```

**持续 2 分钟、12 次探测全部 429** —— 尽管我的探测速率（6/min）低于声称的 10/min。

## 二、这说明什么（诚实推断）

我此前的结论（见 `XZT-RATELIMIT-AND-MODELS.md`）是：
> "端点确实是严格 10 次/分钟/IP 限流，窗口为滚动"
> 依据：连打 12 次，第 11 次起 429。

**那组实验只证明了"每分钟 ≥10 次会触发"，并未排除"更低速率也会触发"或"存在更长的惩罚窗口"。**

本轮数据补充了两点新事实：

1. **`code: "ip_throttled"`** —— 显式错误码，确认是 **IP 级**限流（非模型级、非账号级）
2. **触发后可能进入较长冷却**：我在触发 429 后以 6/min 重试，**2 分钟仍未恢复**
   → 说明 429 后存在**惩罚性冷却窗口**，而不只是"等下一个分钟"

## 三、修正后的理解

| 项 | 原结论 | 修正后 |
|---|---|---|
| 触发阈值 | ~10 次/分钟 | ~10 次/分钟（**这个仍成立**） |
| 窗口性质 | 滚动窗口 | 滚动窗口 **+ 触发后的冷却期** |
| 冷却时长 | 未知（未测） | **≥2 分钟**（本轮观测下限，未测到恢复点） |
| 错误码 | 未记录 | **`ip_throttled`**（IP 级） |
| 对批量探测的影响 | "加节流即可" | **加节流不够**；一旦触发，需**长退避**（≥2 分钟） |

**对工具的含义**：
- 批量扫描应**主动把速率压到远低于 10/min**（如我用的 6.5s 间隔 ≈9.2/min 仍偏冒险）
- 更稳妥：**间隔 ≥10s**（6/min），并把"遇 429 就长时间退避"写入逻辑
- **绝不应把 429 当作"模型不可用"** —— 这是我在前一轮刚修掉的问题，本轮再次遇到

## 四、对池的实际影响（这才是关键）

**池内 xzt 账号（#31/#32）正在承受同样的限流。** 含义：

1. **concurrency=1 无法防限流**（本会话早已指出）：1 req/s ≈ 60/min，远超阈值
2. 一旦被调度到并触发限流，**会长达 2+ 分钟无法服务**
3. 但：**#31/#32 的 priority 是 36/37（垫底）**，实际极少被选中（`usage_logs` 零记录）
4. 且 `error_rate` 避让机制会在 429 累积后自动降权

→ **结论：当前配置下危害有限，但不建议提升其优先级。**

## 五、我未验证的部分（如实标注）

- ❓ **冷却窗口的精确时长**：本轮只观测到"≥2 分钟仍未恢复"，未等到恢复点
- ❓ **触发阈值是否真的是 10/min**：那组实验用的是"快速连打"，
  在"低速长时间"场景下的阈值可能更低
- ❓ **限流是按 IP 还是按 IP+路径**：错误码说 `ip_throttled`，但未验证不同路径是否有独立配额

**这些都需要专门的长时间实验**（代价是持续打满配额），**本轮不做**。
