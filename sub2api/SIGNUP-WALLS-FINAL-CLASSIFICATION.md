## 一、结论：这是**账号资源问题，不是技术问题**

所有可自动化的路径都已穷尽，剩下的墙**不是我能绕过的技术障碍**，而是：

> **每一家都要求一个「能收验证码的真实邮箱/手机」+「过人机验证」**

这两样东西**本质上是身份凭据**，我没有、也不应该去获取。

## 二、注册墙分类（基于实测证据）

### 2.0 ★ NVIDIA NIM 墙的独立验证（本轮新增，此前仅采信并行会话）

上一版对 NIM 的判定是"hCaptcha 交互挑战"，但**那是并行会话说的，我没有独立验证**。
本轮我自己做了验证，**结论成立且有更精确的证据**。

**做法**：抓取 `/signup` 页引用的**全部 46 个 JS**（合并 4.66 MB）分析。

**发现的认证机制**：

```
⚠️ 引入 hCaptcha 脚本                          ← 确认存在人机验证
⚠️ 认证相关路径：
     /v2/login_url
     /v3/users/me/verify
     /v3/otp/verify                             ← ★ OTP 一次性验证码
```

**结论**：NIM 的注册墙是**双重的**——
1. **hCaptcha 人机验证**（自动化设计上过不去）
2. **OTP 验证**（`/v3/otp/verify`，需要能接收验证码的邮箱/手机）

> 这**加强**了"U8 需人工"的判断：即使过了 hCaptcha，还需过一次 OTP。
> 但并行会话称"表单已填好、只差点一次" —— **可能是 OTP 已通过、只差验证码那一步**。
> 具体差几步，**需你实际操作时才知道**。

**同时验证的另一件事**（重要）：
`GET /v1/models` **匿名返回 200 且列出 82 个模型**（本轮及此前多轮一致）。
即 **API 目录公开可读，只差一把 key** —— 这也是它值得你花时间的原因。

## 三、零一万物专项深挖（本轮终结该项，结论：**无法从外部确定**）

上一版把它标为"未确定"。本轮做了 4 轮递进排查，**仍然无法确定**，但已能说清**卡在哪里**。

### 3.1 排查过程与证据

| 轮次 | 做法 | 结果 |
|---|---|---|
| ① | 抓首页 → 只取前 2 个 JS | ❌ **无效**：那是 polyfills + 字体文件（**我自己犯的错，已修正**） |
| ② | 抓全部 5 个 JS（375KB） | ✅ 无任何 captcha 特征；**但也没有任何 `/api/` 路径** |
| ③ | 直探注册路径 | `/login` **200**，但 `/signup` `/register` `/console` `/api-key` 全部 **404** |
| ④ | 抓 webpack runtime 找懒加载 chunk 清单 | ❌ **提取到 0 个 chunk 名**；探常见命名（signup/register/auth）也全无 |

### 3.2 决定性证据

```
① 全部 JS（375KB）中：/api/ 字面量路径数 = 0
② /login 页面（8.7KB）中：注册关键词、验证码关键词 = 均无
③ webpack runtime（4.6KB）中：chunk 映射表 = 空
```

**即：该站点在纯 HTTP 抓取层面「看不见业务逻辑」** —— 接口路径与页面组件**都不在静态资源里**。
最可能的原因：**逻辑在需 JS 执行后才请求的懒加载 chunk 中**，而我没有浏览器执行环境。

### 3.3 最终判定

> **零一万物：无法从外部确认其注册机制（不推断、不猜测）。**

**这不是"无验证码"，而是"看不到"。**
它与已验证的智谱（明确检出邮箱+短信验证码接口）形成对比——
**智谱有证据，零一万物无证据，故两者结论不同**。

**若日后要查清**：需用真实浏览器打开 `/login` 页、观察"注册"入口及其网络请求
（属需要浏览器会话的操作，本轮不做）。

> 📌 **方法论记录**：这一项的价值在于——我**没有**因为"查不到验证码特征"就写成
> "无验证码，值得一试"。**证据缺失 ≠ 证据表明不存在**，两者必须区分。

## 三·五、★ GitHub 注册墙实测取证（2026-09-14 本轮新增，DataDome 铁证）

**背景**：用户提出"注册大量 GitHub 账号进池"。此前判定（ToS 禁自动化建号、GitHub Models
已退役无额度）需要补一条**现场取证**，于是用 CDP 驱动真实浏览器实际打开 github.com/signup
走了一遍注册流程——在验证墙前停死，留下决定性证据。

**实测过程**：
1. 导航 `https://github.com/signup` → 200，先出 Cloudflare `#cmsg` 挑战动画
2. cmsg 消失后表单**始终不渲染**：`inputs=0, forms=0, bodyLen=0`
3. 深查页面结构 → iframe 指向 **`geo.captcha-delivery.com/captcha/`**、加载
   **`ct.captcha-delivery.com/c.js`** —— 这是 **DataDome**（比 Turnstile 更严的动态指纹
   反自动化服务）的前置验证
4. 验证不过 → 注册表单根本不渲染 → 自动化连填表的机会都没有

**对"批量注册"路线的终局判定**：
- 表格都不渲染 = 注册机/脚本自动化在第一道门就死（本取证）
- 打码绕过 DataDome = ToS 违规 + 动态指纹成本极高
- 临时邮箱 = 9-13 已实测触发 10-15 次验证码且过不了
- **唯一可行 = 真人手动 1 个号**（人过验证 → 邮箱收码）—— 与用户"我已注册过 1 个号"吻合

完整取证见 `SIGNUP-WALL-DATADOME-EVIDENCE.md`。

### 4.2 四类墙（无法用代码绕过）

1. **人机验证**（hCaptcha / Turnstile / 极验）—— 设计目的就是拦自动化
2. **邮箱/短信验证码** —— 需要一个真实可收件地址，且多数站禁一次性邮箱
3. **OAuth 登录态** —— 需你的第三方账号授权，我不应擅用你的身份
4. **云账号实名** —— 需身份证/企业认证

> 这四类**不是"我技术不够"**，而是**服务方主动设置的自动化边界**。
> 强行绕过（打码平台、伪造身份、滥用他人账号）属越界行为，我不做。
