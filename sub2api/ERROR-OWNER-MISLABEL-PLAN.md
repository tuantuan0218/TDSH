# 400 错误 error_owner 误标问题 — 2026-09-14（建议文档）

> 来源：`node pool-health-check.mjs` 巡检（2026-09-14），数据见 `POOL-HEALTH-REPORT.md` §5。
> **本建议不执行**——涉及调度口径，等你批准。

## 问题

近 12h **400 错误 356 条全部被归 `error_owner=provider`**，但逐类分析显示**绝大多数是客户端请求问题**：

| 类别 | 数量 | 占比 | 实际归属 |
|---|---|---|---|
| 超上下文窗口 | 300 | 84.3% | **client**（请求太长，非上游故障） |
| 工具调用 name 为空 | 39 | 11.0% | **client**（请求构造非法） |
| 其它 | 13 | 3.7% | 需抽查 D 桶 |
| 请求体缺字段 | 4 | 1.1% | **client**（请求不完整） |

**危害**：若调度器按 `error_owner=provider` 做账号降权/健康分扣减，
会**错误惩罚无辜上游账号**（真正的原因是发来的请求超长/非法，不是上游坏了）。

## 证据链

1. 400 响应由网关对**请求**做校验后直接产生（无需上游参与即可判 400）
2. `error_owner` 字段语义 = 错误归属方；400 的成因多在请求侧（超上下文/非法 tool_call），
   却统一落 provider → 语义失真
3. 池内已知先例：`AGENES-CONTEXT-LIMIT-FIX.md`（460 条/7天必然 400 因超上下文被派 551K~1M 请求）——
   **这是客户端超上下文，不是 agenes 上游故障**，却会因误标拖累其健康分

## 建议（需批准）

### 方案 A：语义识别后归 client（推荐）

在错误记录逻辑中，对 400 按请求体特征分流：
- `max_input_tokens` 超上游上限 → 归 client（超上下文）
- `tools[].function.name` 为空 / message 缺字段 → 归 client（非法构造）
- 其余 400 保留 provider（如上游返回的 400 响应体）

预期效果：健康分/降权不再被客户端请求污染；上游真实故障仍能准确暴露。

### 方案 B：仅调口径不改代码

`error_owner` 保持现状，但**账号降权/健康分计算排除 400**（只按 5xx/429/超时 计上游故障）。
改动面更小，但会掩盖"上游确实返回 400"的边缘场景。

## 影响面与验证

- 影响：调度器打分（error_rate 权重 0.8）、账号健康分、Ops 面板上游错误率
- 验证：改后重跑 `node pool-health-check.mjs`，核对 400 段不再全归 provider；
  抽查 D 桶 13 条确认无漏网
- **✅ D 桶已抽查（2026-09-14 实测）**：`ops_error_logs` 近12h status=400 非超上下文/
  非 tool_call 样本真实成因 = **请求体解析失败**（`Invalid request body` /
  `Failed to read request body`），与超上下文/非法 tool_call 同属**客户端问题**——
  无被误归进 D 的上游主因，"400 绝大多数是客户端问题"分类结论成立
- 回滚：改一处判断即可，无数据迁移

## 处置

批准后定位网关错误记录代码（`error_owner` 赋值处，pool 报告 §5 同源），
按方案 A 加 400 语义分流；或你给 admin key 走配置开关（若支持）。
