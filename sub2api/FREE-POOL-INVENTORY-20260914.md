### ③ 编码教训（第 N 次，这次给出可执行判据）
PowerShell `>` 写出的日志第 1/2 字节 = `0xFF 0xFE` → **UTF-16LE BOM**；node 以 `utf8` 读必乱码，

**更稳的做法（本轮起采用）**：**绕开 PS 重定向，直接读 node/脚本自己写的 UTF-8 产物**（如 `screen-latest.json`），

## 发现 70（实测 01:1x）：签到限流的可控化 —— **我原来的"免登录"方案被实测否掉，换成两个真起作用的机制**

### ① 我先想错了一次（并且是自己测出来错的）
看到 41 个号 `AUTH_SESSION_LIMIT`，我的第一反应是"**复用 store 里缓存的 accessToken，就别每天登录了**"。
实现后小样验证：`缓存令牌命中 0 / 实际登录 3`。本地解 JWT 才知道原因：
```
payload 键 = token_use, sid, uv, sv, iss, sub, aud, exp, nbf, iat, jti
sub = 757（uid 能解出来，说明请求头是对的）
iat 10:20:35Z → exp 10:35:35Z  →  TTL = 900 秒（15 分钟）
```
→ **columbina 的 access_token 只活 15 分钟**，所以"每日签到免登录"在物理上不成立。
→ **保留该分支**（命中就用，成本一次 GET），但**不再把它当作解法**；记下的设施事实是：**令牌 TTL 900s，签到必然重新登录**。

### ② 真正能落地的两个机制（已实现并实测其一）
1. **用完登出释放会话**：签到流程结束即 `POST /api/user/logout`；若该 fork 无此口（404）则记住不再白试。
   ⚠️ 诚实标注：**这一条本轮无法验证**——被拒的号拿不到有效会话，无从测试；等明日有号能登录时由 `登录方式` 那行输出与后续成功率体现。
2. **连续失败即熔断（实测有效）**：`BREAK_AT=4`，实跑：
```
   #0 / #1 / #3 / #4 → 登录失败 AUTH_SESSION_LIMIT ×4
   ⏹ 连续 4 个号失败（多为 AUTH_SESSION_LIMIT）→ 本轮熔断停止，不拿几十个号去硬撞。剩余号明天再签。
   登录方式：缓存令牌命中 0 个（零登录）· 实际发起登录 4 次
   🔴 登录失败 4 个，分类: AUTH_SESSION_LIMIT×4
```
→ 加上号间隔 2.5s。**意义**：以前一次跑会连着撞 41 次登录（每次都可能新开会话），现在最多 4 次就收手——**这是在同站同 IP 条件下唯一能降低限流压力的做法**。
→ 另加 `ONLY=N` 小样模式：以后改完这个工具我先只跑 3~8 个号验证，不整批打站方。

### ③ 判读与决策（写下来，免得未来会话误判）
`AUTH_SESSION_LIMIT` 集中出现在**我今天登录次数最多的那批老号**（#0/#1/#3/#4/#5/#6），
而 13 个中后段号仍签到成功 → 支持"**按账号累计活动会话**"的解释，而不是"整站 IP 封禁"。
→ 所以：**继续在同站加号 = 提高被拒概率**（与发现 69 的"边际收益转负"一致）。
